## Harness 设计讨论（核心，影响整个项目方向）

与用户完成了一场关于"AI 开发 harness"的完整讨论，并对照了参考项目

cba_game 敲定了 harness 设计方案。关键结论：

### harness 是什么
让 AI agent 在受控、可重复、可观测环境下自助闭环工作的环境与规则层。
心智模型：定义"地形"(上下文)、"裁判"(验证)、"围墙"(护栏)，不定义"路线"(具体方案)。

### 三维结构
- 复用层：L1 通用(~/.workbuddy) / L2 技术栈模板 / L3 项目层，靠回流演进。
- 功能层：上下文层 / 验证闭环层 / 流程层(skill) / 人机协作层；hooks 横切护栏。
- 客户端层：契约层(进 git、中立、全客户端共享) + 绑定层(每客户端一份薄适配) + CI 兜底。

### 关键原则
- 判断 vs 执行：文档塑造判断，hook 框住执行，脚本做机器裁判。
- 机制与知识分离：机制(脚本)与知识(规则正文)分开，路由表是唯一汇合点。
- 工作流(dev_mode)是第四个路由维度：UE 项目可用 GameMode 或 ExperienceFramework
  两种玩法工作流，需按"在做哪种开发"路由，不只按路径。
- 薄壳 skill：skill 正文不含内容，只指向 docs 真相文件(跨客户端、防污染)。
- 拦截点计算 > 事件驱动：授权在 PreToolUse 写前拦截点机械强制，弱 hook 客户端也能用。

### HET 经验教训

  但8模块引擎不必要——其核心价值可用"一个stage数据字段+scope_guard写前判定"拿到。

### cba_game 落地共识

- scope_guard 一个脚本覆盖三件事：路径授权 + dev_mode路由 + stage阶段权限。

### 后续讨论的关键修正（同日晚）
1. **workflow = skill**：dev_mode 工作流不另建 docs/ai/workflows/ 层，直接用 skill 承载
   （单客户端阶段合并，避免冗余；多客户端时再抽 docs 真相+薄壳指针）。
   职责划分：skill 管"选哪条路"(判断)，scope_guard 管"现在让不让动手"(执行)。
2. **补 spec 入口阶段**：完整流程是 澄清→spec→执行→验证，不是从执行开始。
   - spec-intake skill：接需求先澄清边界/工作流/约束，按模板生成 spec。
   - spec 含：做什么/不做什么/涉及工作流/验收标准(机器可判优先)/爆炸半径。
   - **dev_mode 在 spec 阶段定下并写进 spec**，作为执行阶段匹配工作流的权威依据
     （比执行时临时判断可靠）。
   - scope_guard 在 design 阶段强制 writable:false + require_spec → spec未确认写不了代码
     （"spec前置"从建议变机器强制，等价于HET的Intent.Idle但用轻量stage字段）。
3. **AI 工作流引导链**：领域特定流程(PSD→JSON→UMG、GAS接入、网络同步等)都要喂成
   skill；工作流之间可互相引用形成引导链；harness给机制，领域知识靠喂。

### git 提交门禁的分层（补充，重要）
- 阶段0 的 AI hook 应为 3 个不是 2 个：
  PreToolUse(Write|Edit)→scope_guard / PostToolUse(Write|Edit)→编译 /
  **PreToolUse(Bash)→pre_commit_guard(git commit前跑编译+scope+spec检查)**。
- git 提交的主力防线是 **git hook(.githooks/)** 不是 AI hook：
  AI hook 只在AI经WorkBuddy调Bash时触发，可被绕过/手动commit绕过；
  git hook(pre-commit编译+禁区 / commit-msg格式)无论谁提交都拦，是硬防线。
- 但 cba_game 当前还不是 git 仓库，git hook 依赖仓库存在 → 列入阶段2(上git时)再建。
- 原则：质量门禁分两层 = AI层(settings.json,软,即时反馈) + 系统层(.githooks,硬,最终防线)。

### 治理层的"添加方式"（元规则——用户举例只是示意，这才是重点）
用户明确：之前举的 UI工作流/PSD→UMG/Experience模式 只是例子，核心是将来添加新东西的统一方法：

1. **新增一类工作流/领域流程** → 加一个 skill（薄壳：描述写"何时触发"+正文步骤+验证）。
   放 .workbuddy/skills/；多客户端时再抽 docs 真相+薄壳指针。
2. **新增一条路径/禁区约束** → 改 harness/policy/scope.yml 的 allow/deny（数据，不动代码）。
3. **新增一个架构约束(某类文件该怎么写)** → 加 docs/ai/rules/xxx.md + scope.yml 的 path_rules 挂路由。
4. **新增一个可机器判的检查** → 加 harness/scripts/xxx_check.py(CLI) + 挂到 hook/CI。
5. **新增一个hook** → 只在痛点出现时注册，matcher+command指向harness脚本；客户端支持27+事件但只按痛点挂。
6. **新增阶段/模式** → 改 scope.yml 的 stages/dev_modes 数据字段。
统一原则：**机制(脚本)不动，知识(数据/skill/docs)生长；路由表(scope.yml)是唯一汇合点；
每个新增都要答"它解决的痛点出现了吗"。**

### 编译闭环 build_editor.py（照HET改进+超越，已实测全链路）
用户问"AI能否像Rider点Build一样拿到编译日志报错"。过程与结论：
- **build_editor.bat → build_editor.py**（.bat含中文在cmd下自爆；且改Python与harness其他脚本统一）。
- 照HET check_build_compile.ps1：直接调 `UnrealBuildTool.exe`(带-FromMsBuild)而非Build.bat；
  输出落盘(非管道)防编码崩；UTF-8读回；识别UBT/编译/MSBuild/UHT四类失败。
- **关键发现**：UE5.9源码引擎用UBA分布式编译，会把cl.exe的具体错误(error Cxxxx)吞掉，
  stdout/stderr/Log.txt都只有"Exited with error code 1"。-NoUba/-Verbose都拿不回。
- **解法(方案2,已实现)**：编译失败后从UBT输出找失败的.rsp，用vswhere定位cl.exe重跑该.rsp，
  cl直接输出`文件(行,列): error Cxxxx: 描述`(cl错误本来完整，是UBT/UBA吞了)，提取给AI。
- cl.exe(MSVC)输出GBK中文，用GBK解码(错误号+符号名+位置全ASCII清晰，中文描述小瑕疵可接受)。
- 实测：注入错误→拿到`cba_game.cpp(9,42): error C2065: UndefinedType`等Rider级具体错误；
  恢复→清Intermediate缓存→PASS(0 errors,0 warnings)。pre_commit_guard也改用build_editor.py并验证通过。
- 全项目同步：.bat引用全改.py（AGENTS.md/README/spec.md/settings.json/pre_commit_guard）。
- 坑：UE增量编译缓存失败状态，改了源码要清Intermediate对应模块缓存才重编。
- 待办：ENGINE_ROOT可选(build_editor.py默认D:\UnrealEngine已可用)；git init后建.githooks/(阶段2)。

### ★ Lyra 式统一架构重构（2026-07-21，力度3，用户多轮辩论驱动）
用户连续追问推翻了 asset_rules/A方案 的窄化设计，最终确立 Lyra 式统一架构。
**辩论关键转折（用户胜出）**：
- "约束少时B(通用引擎)跟A(判定器集合)体量差不多" → A的"更轻"假设不成立。
- "B的膨胀可通过设计规避(参考Lyra StateTree/GameplayTag/GA_Phase封闭schema)"。
- "删除即回收：B删skill就删了对应约束；A把约束焊进机制代码,删skill约束残留" → A的结构性缺陷。
- 结论：B(schema封闭的声明式求值器+约束随宿主生灭)优于A。

**Lyra 模式精髓（参考 LyraStarterGame/引擎StateTree源码）**：
逻辑封闭(C++虚函数/求值器写死) + 数据开放(InstanceData实例填) + 配置封闭枚举(bExactMatch/Operand) +
实例一文件一生灭。HET膨胀根源=把组合逻辑也放进数据(YAML可表达控制流=YAML编程)；Lyra只让数据填
"实例数据+枚举开关",组合逻辑也只是二选一枚举。

**统一元原则(已写入harness/README.md顶部)**：每个可扩展点=声明式约束节点，满足
逻辑封闭/数据开放/配置枚举/实例生灭(随宿主)。
