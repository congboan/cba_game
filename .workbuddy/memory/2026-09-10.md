### 发现的覆盖缺口（P1）
provider 声明的 `path_field: arguments.AssetPath` 与真实 MCP 工具参数命名**不匹配**，且三种命名风格并存：
- Python toolset（`editor_toolset.*`）：snake_case — `asset_path` / `file_path` / `path` / `new_path` / `asset_paths`
- C++ toolset（`SettingsFrameworkEditor.*`、`UMGToolSet` 等）：camelCase — `assetPath`
- root skill 声明：PascalCase — `AssetPath`（三者无一命中）

链路后果：`operation_normalizer._provider_effect_requests` 在字段缺失时执行 `if not values: continue`（静默跳过该 effect）→ MCP 调用**永不产生 pre_write evaluation request** → 所有 `when: pre_write` 约束对 MCP 写入全部失效：`.uasset`/`.umap` capability 门禁、`path_writable_stage`、`check_spec_required`、`check_generated_include`、`check_ue_naming`、gf-location/dependency、引擎只读、`authoring-required`。
且全部 18 条约束中**无一条 `when: pre_tool`**，故 provider 的 `unresolved_events: [pre_tool]` 在 `_unresolved_event_blockers` 中找不到 blocker → abstain 放行。
结论：MCP（含 `AssetTools.write_file` / `delete` / `move`）是当前唯一完全不受路径、阶段、spec 范围约束的写入通道。

### 待决策
provider schema 的 effect 只允许**单条** `path_field`，无法表达候选字段名列表 —— 这是机制层限制，修法需用户在治理任务中定夺（改声明 / 加 `when: pre_tool` 兜底 / 扩展 effect schema 支持候选字段或按 toolset 分 provider）。修改 root skill 属治理任务，需 `governance-authoring` 且写入 `.workbuddy/skills` 逐次人工确认。

## hook stdin 截断复核结论（用户质疑触发，待最终定案）

**触发**：用户提出「这未必是 WorkBuddy 的问题，因为没用这套 harness 的项目没出现过」。
复核后发现：旧归因（客户端序列化截断、harness 无法修复）的实验基础不成立，但新机制也尚未证实。

**旧归因失效的两条证据**

1. 2026-08-12 那次「决定性实验」：用户用 PowerShell 手工喂 500+ 字符中文载荷给
   `scope_guard.py --hook-stdin`，得到「正常解析」结论。但 PowerShell 管道给原生命令的默认编码
   会把中文降级为 `?`，送达 python 的已经不是同一条 UTF-8 载荷 —— 该对照实验零信息量。
2. 2026-08-11「column 410 = 载荷长度处截断」被当作长度阈值证据，实为巧合读数。
   今天实测：约 10-11KB **纯 ASCII** Write 载荷完整通过（落盘 11009 字节，末行到达），
   直接否掉「约 441-797 列截断」这一阈值模型。截断点与阈值都不是长度决定的。

**今天确认的新事实**

1. 客户端写入路径干净：`codebuddy-headless.js` 的 hook 执行器是
   `JSON.stringify(payload)` → `stdin.write(str)` → `stdin.end()`，无 slice、无长度上限、
   不转义非 ASCII。载荷组成含 `session`（整个会话对象）与 `buildAgentTrigger`。
2. 失败与**内容**强相关、与长度无关：中文 Edit 多次 abort（列号 1170 / 789 / 624，随载荷增减），
   而 11KB 纯 ASCII 通过。
3. 环境事实：hook 用的 python 是 anaconda 3.11.4；`locale default = cp936`；控制台
   `stdin encoding = utf-8`（PEP 528 只覆盖控制台，管道仍走 locale）。
4. cp936 假设被对齐扫描否掉：12 个 CJK 变体在 cp936 下 **全部 UnicodeDecodeError 崩溃**、
   0 个「静默吞字符」。若 hook 真按 cp936 解码，症状应是崩溃 + traceback，而不是
   `hook_payload.invalid_json`。所以「harness 的 stdin 按 GBK 解码」也不成立。

**现状**：完整载荷 + 正确解码两个前提同时成立时 JSON 必能解析，因此剩余唯一自洽解释是
「hook 边界上收到的文本被某种会丢字符但不抛异常的转换处理过」。已装最小插桩抓原始字节定案。

与 root skill 两处「客户端 bug / harness 无法修复」的记载。

## 触发实验：转义相关性（1）

假设：失败与载荷中**必须被 JSON 转义的字符**相关（ASCII 双引号 `"`、反斜杠 `\`、换行）。
本段故意包含裸引号 " 与反斜杠 C:\Users\PS 与 \n \t 形式的文本，用于对照检验。
已知：11KB 纯 ASCII 探针（无引号无反斜杠）通过；今天数次含引号/反斜杠的中文 Edit 失败。

## 截断根因定案与修复（20:30，已实锤）

**根因**：`scope_guard.py` 用 `sys.stdin.read()` 读 hook 载荷，文本流按进程 ANSI 编码
（zh-CN 下 cp936）解码客户端发来的 **UTF-8** 字节。3 字节 UTF-8 与 2 字节 GBK 节奏错位后：

- 落在 <0x40 的字节被替换成 `?`（宽容替换，不抛异常）；
- 落在合法 GBK 尾字节区（如 `\` = 0x5C）的字节被**静默吞掉**。

吞掉 `\"` 里的 `\` 会让紧跟的 `"` 变成字符串终止符 → JSON 从中间断裂 → `hook_payload.invalid_json`。
ASCII 载荷无错位、不受影响 → 11KB 纯 ASCII 通过。**长度从来不是变量。**

**物证**：插桩抓到失败载荷原文（`Saved/hook_stdin_last.txt`：936 字符 / 1197 UTF-8 字节 / 0 个
U+FFFD）。`content` 是 `机制细化` 的 UTF-8 字节按 GBK 解出的乱码 `鏈哄埗缁嗗寲`；`瑙? UTF-8` 是
`解 UTF-8` 的 `?` 替换；`锛沑n` 是 `；\n` 的反斜杠被吞。**载荷首尾都完整 → 不是截断。**

**修复（harness 侧 2 处）**

1. `_read_hook_stdin()`：改读 `sys.stdin.buffer` 并按 `utf-8-sig` 显式解码，失败回退 locale，
   两者皆失败 fail-closed 报 `hook_payload.decode_failed`；替换原 `sys.stdin.read()`。
2. `_eval_script()` 的 ctx JSON 改 `ensure_ascii=True`：门禁脚本各自按 locale 解码 stdin，
   发 ASCII-safe 文档可跨任意 8-bit 编码逐字节无损，一处覆盖全部 7 个 checks 脚本。

**验证**：同一失败载荷原件重放 → 通过；落盘内容逐字正确（`<0x40`、`\"`、`>=0x40`、`\` 全保留）。
另有约 500 汉字的本段写入也通过（修复前同类载荷稳定 abort）。

**结论**：用户直觉正确——不是 WorkBuddy 客户端的问题。客户端 `JSON.stringify` + `stdin.write`
方向一直是干净的；缺陷在 harness 的 stdin 解码与 gate 通道的编码约定。
