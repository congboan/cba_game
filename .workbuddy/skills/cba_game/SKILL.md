# cba_game

UE5 Lyra-style basketball game project.

## 命令行执行规范（所有 Bash/PowerShell 命令）

harness 的 `operation_normalizer.py` 只能静态解析**纯命令**。复合命令（含 `cd ... && ...`、`;`、`|`、`2>&1`、`&&`、`||`、变量赋值、`echo $?` 后缀等）无法被静态解析，会被判定为 `unresolved` 并拒绝执行（`HARNESS_OPERATION_UNRESOLVED`）。

**AI 在会话内执行任何命令必须遵循：**

1. **单条命令，不加 shell 组合**。禁止 `cd && cmd`、`cmd; echo $?`、`cmd | head`、`cmd 2>&1` 等复合形式。
2. **程序与参数都用绝对路径**（python 解释器、脚本、文件路径）。避免依赖 `cwd` 或 PATH 解析。
3. **需要切换目录时**：不写 `cd ... && ...`，而是用绝对路径直接调用目标（如 `python E:/project/harness/scripts/build_editor.py`），工具的 `cwd` 由工作区上下文提供。
4. **需要查看输出时**：直接执行命令读取完整输出，不用 `| head` / `2>&1` 截断或重定向（这些是 normalizer 无法解析的复合形式）。
5. **受信脚本**：`harness/scripts/` 下的 `build_editor.py`、`launch_editor.py`、`scope_guard.py`、`resolve_engine.py`、`init_root_skill.py` 是 normalizer 内置的 `trusted_harness_wrapper`，**必须用纯命令形式调用**（绝对路径 python + 绝对路径脚本）。这样 AI 可以自己重新编译并刷新 `Saved/harness_last_build.json`，无需人工在外部执行。

**为什么**：`build_freshness` 门禁（`project.build.stop` / `project.build.pre-commit`）在 Stop / commit 时比对当前源码指纹与上次成功编译指纹。AI 源码变更后需要自行调用 `build_editor.py` 刷新指纹；若调用形式无法被 normalizer 静态识别，harness 无法证明副作用，会拒绝调用，导致门禁无法解除。

**Rider / IDE 集成说明**：Rider 加载项目时若检测到源码晚于上次成功编译（`Saved/harness_last_build.json` 指纹不匹配），会提示需要 build——这是 `build_freshness` 的同一保护逻辑在 IDE 侧生效，属正常行为。源码变更后重新编译即可消除。

## 编辑器启动验证

`build_editor.py` 只验证 C++ 编译通过（UBT 无错误）。编译成功后编辑器仍可能因以下原因启动失败：

- 模块初始化崩溃（`StartupModule()` 空指针等）
- 插件加载失败（依赖缺失、版本冲突）
- 配置错误（`DefaultEngine.ini` 格式问题）
- 缺少运行时 DLL

`launch_editor.py` 在编译通过后做编辑器烟雾测试：

```bash
python harness/scripts/launch_editor.py
```

行为：
- 以 `-unattended -nullrhi` 模式启动 UnrealEditor.exe（无渲染、无交互，快速验证）
- 监控 stdout 等待 `LogInit: Engine is initialized` 标志
- 检测 10 类启动错误（FatalError、ModuleLoadFailed、PluginLoadFailed 等）
- 300 秒超时防止挂起
- 成功/失败记录到 `Saved/harness_last_launch.json`

**AI 在源码变更后的完整构建流程**：

1. `python harness/scripts/build_editor.py`  → 编译
2. `python harness/scripts/launch_editor.py` → 启动验证

## WorkBuddy hook stdin JSON 截断规避（认知约束）

WorkBuddy PreToolUse hook 对长 Write/Edit payload 的 stdin JSON 序列化会在约
441-797 列截断，产生 `hook_payload.invalid_json` 与 `HARNESS_TASK_ABORT`。
截断发生在 scope_guard 收到 stdin 之前，harness 无法在机制内修复；AI 必须
认知规避，不得把 abort 误判为治理故障。

**执行规范**：

1. 长文件写入/编辑一律分段小操作，每段 payload 控制在约 200 字符内
   （实测 Edit 的 old_string/new_string 合计超 700 字符即触发）。
2. 命令行参数避免长中文内容（UTF-8 多字节加剧截断），如 git commit message
   改用短 ASCII 或 `-F <file>` 从文件读。
3. 触发 `invalid_json` abort 后：任务终止是协议要求，禁止降级放行、禁止换
   未适配入口绕过；等待用户确认后重新发起（分段小写入即可正常完成）。

**为什么**：hook stdin 是治理门禁信任边界（见 harness/decisions.md 对应 ADR）。
该问题真实修复点在 WorkBuddy 客户端序列化，不在 harness 侧。
